● Locked template · Single source of truth

The Recipe Card Template.

This file is the canonical recipe-card template for Provenance. Every fix-list sprint that touches recipe rendering edits THIS FILE — never rewrites from scratch. Card and detail views read from the same data model. Sample cards below show every state the card can hold.

Rule 1. Edit, never rewrite. Rule 2. Card and detail share one schema. Rule 3. State changes via tag, not template clone. Rule 4. Pat's Rule on every ingredient. Rule 5. Seven pillars, no fewer, no more. Rule 6. Language column from day one.
Why this file exists. Recipe cards are the user's primary surface in Provenance. They are where users land, where they import, where they enhance, where they cook from, and where the supplier flywheel lives. In every prior rebuild, recipe cards drifted because there was no single template to edit. This is that single template. The data model, the card scale, and the detail scale all live here. If you change the way a recipe is rendered anywhere on the platform, you change it here first.

I. The data model

What every recipe holds
id
UUID. The recipe's permanent identifier. Never changes.
slug
URL-safe slug from the title. Used at /recipe/<slug>. i18n-aware: slug is generated from the recipe's primary language. Language-prefixed routes (/ja/, /fr/, etc.) resolve to the same recipe id.
language
ISO 639-1 code. Primary language of the recipe (en, ja, fr, pt, es). Even at English-only launch, this column exists. Future translations bind to the same recipe id with different language values.
state
One of: imported, enhanced, canon, composed, member. Drives the card tag and dictates which pillars are required vs. optional. Changes via state transition, not template clone.
title
Display name. May include italic span: "Pan-Seared Duck Breast with mānuka honey glaze" — the italic carries lyrical content, Playfair italic, charcoal-soft.
cuisine
FK to cuisine canon. Drives the canon tag on the card. A recipe belongs to one cuisine canon as its home; cross-cuisine parallels are referenced separately in Pillar V.
image_url
Hero image. Card view uses 4:3 crop. Detail view uses full image. One image, two renderings — never separate uploads.
cooking_time_minutes
Total time including prep. Displayed on card meta strip.
serves
Default serving count. Cost This Recipe and Menu Builder calculations scale from this base.
requires_haccp
Boolean. Detected server-side by _detect_raw_served(). When true, the terracotta HACCP badge appears on the card and the HACCP brief surfaces in the detail view's sidebar.
pillar_1_ingredients
Structured list. Each ingredient holds: name, quantity, unit, origin_supplier_id (the named producer), provider_supplier_id (the local distributor). Pat's Rule applies here — both pointers populated where canon has them.
pillar_2_method
Ordered list of steps. Each step holds: instruction, sensory cues (sound/smell/texture/visual), optional timer_seconds, optional tool references.
pillar_3_quality_hierarchy
Reserve vs House substitution map per ingredient. What the swap costs in technique adjustment.
pillar_4_sensory_tests
Pass/fail anchors at the critical moments of the cook. The eye-of-the-needle cues.
pillar_5_cross_cuisine_parallels
Linked technique references in other canons. Drives the "this technique elsewhere" section.
pillar_6_beverage_pairings
Three role-labelled pairings minimum (complement, contrast, non-alcoholic). Each holds origin_producer + local_provider — Pat's Rule for beverages.
pillar_7_origin_lineage
The dish's home, travel history, apprenticeship lineage, authority sources cited.
owner_user_id
For member recipes (state = imported/enhanced/member/composed). NULL for canon recipes. Drives "Your Recipe Collection" vs "From the Canon" filtering on /kitchen.

II. The seven pillars

The Sashimi Standard schema
I
Ingredients
Named producers, species-level precision. Pat's Rule: origin + provider.
II
Method
Numbered steps with sensory anchors. What to listen for, smell, feel.
III
Quality Hierarchy
Reserve vs House per ingredient. What the swap costs.
IV
Sensory Tests
Pass / fail at the critical moments of the cook.
V
Cross-Cuisine Parallels
Where this technique lives elsewhere. Genuine connections only.
VI
Beverage Pairings
Role-labelled: complement, contrast, non-alcoholic. Pat's Rule applies.
VII
Origin & Lineage
The dish's home, travel history, authority sources cited.
⎯
No eighth pillar
The schema is closed. Additions go inside a pillar, never beside it.

III. The five states

A recipe is always in exactly one state
recipe · the canonical template (this file)
↓

Reserve-generated

State transitions: Imported recipes become enhanced when the user fills in pillar gaps; composed recipes become enhanced when the user edits them; member-contributed recipes become canon when verified against the Sashimi Standard. Canon recipes do not transition out — they may be revised in place but stay canon. Every state uses the same card template. Only the tag changes, and the pillar dots reflect how many pillars are populated.

How to add a new state

If a new card state is needed (e.g. "draft" before publishing), add it as a new state value in the data model, add a tag style in the CSS block above, then add a sample card here. Do not clone this file. Do not create a parallel template.

V. Card vs detail · same data, two scales

One template, two renderings
Card scale (above) renders: image, state tag, optional HACCP badge, cuisine, title, three meta items, pillar-fill dots.
Detail scale (full /recipe page in main wireframe deck) renders: the same data expanded — all seven pillars in full, sidebar with HACCP/cost/tools, action buttons for Cook Mode / Edit / Save / Suggest Supplier.
The rule: the card is a projection of the detail. Never invent a card-only field. Never invent a detail-only field. If a piece of data should appear on the card, it goes in the schema first.
Pat's Rule rendering — geographically transferable: on the card, ingredient suppliers are not visible — the card is the hook, not the spec sheet. On the detail page, every ingredient with a populated origin_supplier_id and provider_supplier_id renders as a gold-underlined link. Geographic filtering applies at render time: the provider shown is the user's region's provider, not a fixed one. This is what makes Pat's Rule transferable across geographies — the same data row renders different providers to a Vancouver chef, a Charleston chef, a Tokyo chef.
i18n forward-compatibility: the data model holds a language column on every recipe. Today every row is en. When Japan launches, Japanese-language recipes are added as new rows with language='ja', bound to the same parent recipe id where applicable. The card and detail templates remain unchanged — they render whatever language matches the current locale. The translation work is content, not code rewrites.

VI. Rules of engagement

For every fix-list sprint touching recipe rendering
Rule 1
Edit, never rewrite. If a sprint touches recipe rendering, it edits this file with surgical changes. Never delete and rebuild. Never create a parallel template.
Rule 2
Card and detail share one schema. No data point exists on one view and not the other. Card omits by choice (projection), not by absence.
Rule 3
State changes via tag, not template clone. An imported recipe becomes enhanced by changing its state value and filling more pillars — not by being copied into a new file.
Rule 4
Pat's Rule on every ingredient that has it. Origin + provider, geographically filtered. Beverages too — the same discipline applies.
Rule 5
Seven pillars, no fewer, no more. The schema is closed. Card pillar-dots always render 7 positions. If an entry is missing a pillar, the dot is empty — the schema doesn't shrink to fit.
Rule 6
Language column lives in the schema from day one. Even at English-only launch. When a market opens, translations become new rows, not a new template.
Rule 7
Before opening a fix-list ticket that touches recipes, open this file. If the change cannot be made by editing this file, the change is wrong.
